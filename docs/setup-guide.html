Setup guide

Sentriq on a clean Linux host · step by step

Ubuntu 24.04 LTS Docker Compose ~45 minutes every step has a check you can run

This is the build order that produces a deployment you can hand to an auditor: hardened host, key-only access, a real domain and certificate, the database on UTC, backups that run on a schedule and a restore that has actually been tried. Follow it top to bottom — later steps read values produced by earlier ones.

Before you start You need four things: a fresh Ubuntu 24.04 server you can SSH into, an SSH key pair on your laptop (not a password), a domain or subdomain you can add a DNS record for, and 45 minutes. A 1 GB server will run it, but Postgres plus a rebuild on the same box wants 2 GB.

00What you are building

One host, one compose project, no published app port. The database and the app talk over a private Docker bridge; only nginx is reachable from outside.

01Harden SSH before anything else

A new server is being scanned within minutes. Do this first, and keep your current session open until the new one is proven.

1.1 Create a service account

adduser --disabled-password --gecos "" sentriq
usermod -aG sudo sentriq
mkdir -p /home/sentriq/.ssh
cp /root/.ssh/authorized_keys /home/sentriq/.ssh/authorized_keys
chown -R sentriq:sentriq /home/sentriq/.ssh
chmod 700 /home/sentriq/.ssh && chmod 600 /home/sentriq/.ssh/authorized_keys
Check — from your laptop, in a new terminal 
ssh sentriq@YOUR_SERVER_IP 'sudo -n true && echo "key login + sudo OK"'
Do not continue until this prints key login + sudo OK. Closing the root session before this works locks you out.

1.2 Turn off password and root login

sudo tee /etc/ssh/sshd_config.d/99-hardening.conf >/dev/null <<'EOF'
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
X11Forwarding no
EOF
sudo sshd -t && sudo systemctl reload ssh
Check 
sudo sshd -T | grep -E '^(permitrootlogin|passwordauthentication)'
# permitrootlogin no
# passwordauthentication no

02Firewall, brute-force protection, patches

sudo apt update && sudo apt -y upgrade
sudo apt -y install ufw fail2ban unattended-upgrades curl ca-certificates

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw --force enable

fail2ban with a stricter jail than the default:

sudo tee /etc/fail2ban/jail.d/sshd.local >/dev/null <<'EOF'
[sshd]
enabled  = true
maxretry = 4
findtime = 10m
bantime  = 1h
EOF
sudo systemctl enable --now fail2ban
Check 
sudo ufw status | head -8
sudo fail2ban-client status sshd | head -4
sudo systemctl is-enabled unattended-upgrades   # enabled
Why ufw is safe with Docker Docker publishes ports by writing its own iptables rules that bypass ufw. That only matters for ports published on 0.0.0.0. Sentriq publishes 127.0.0.1:8080, so nothing can be exposed behind ufw's back — which is why the loopback bind in the compose file is not a nicety.

03Install Docker

curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker sentriq
Check — log out and back in first, so the group applies 
docker version --format '{{.Server.Version}}'
docker compose version
# a version number, then v2.x or newer

04Get the code onto the host

Run everything from a fixed path. /opt/sentriq is used here and in every later step.

sudo mkdir -p /opt/sentriq && sudo chown sentriq:sentriq /opt/sentriq
sudo -iu sentriq
git clone https://github.com/ethanx01-H/Sentriq.git /opt/sentriq
cd /opt/sentriq
git checkout v1.4.3          # or the tag you intend to run — not `main`
git log --oneline -1
Deploy a tag, not a branch A branch moves under you and cannot be rolled back to a known state. If you already publish images from CI, skip the build later and set SENTRIQ_IMAGE=registry.example.com/sentriq:1.4.3 in .env — the compose file prefers it over a local build.

05DNS and the certificate

Point the record first; certificate issuance fails until DNS resolves.

# at your DNS provider: an A record for the host you will serve
sentriq.example.com.   A   YOUR_SERVER_IP
Check — wait until this returns your server IP 
dig +short sentriq.example.com

Install nginx, then serve only the ACME challenge so certbot can validate while nginx stays up — this is what makes renewals work without stopping the web server.

sudo apt -y install nginx certbot
sudo mkdir -p /var/www/certbot

sudo tee /etc/nginx/sites-available/sentriq >/dev/null <<'EOF'
server {
    listen 80;
    listen [::]:80;
    server_name sentriq.example.com;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }
    location / {
        return 301 https://$host$request_uri;
    }
}
EOF
sudo ln -sf /etc/nginx/sites-available/sentriq /etc/nginx/sites-enabled/sentriq
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx

sudo certbot certonly --webroot -w /var/www/certbot -d sentriq.example.com \
  --agree-tos -m soc@example.com --no-eff-email
Check 
sudo ls /etc/letsencrypt/live/sentriq.example.com/
# cert.pem  chain.pem  fullchain.pem  privkey.pem
sudo systemctl list-timers | grep certbot   # renewal is scheduled

06Start Postgres first — you need its gateway address

The app refuses to start in production without TRUSTED_PROXIES, and that value is the Docker bridge gateway, which does not exist until the network is created. So: bring up the database, read the gateway, then write the rest of .env.

cd /opt/sentriq
mkdir -p data backups
chown -R 100:101 data backups        # the container runs as uid 100
chmod 750 data backups

cp .env.example .env && chmod 600 .env

# generate the database password now and keep it — step 07 must use the same value
DB_PW=$(openssl rand -hex 24); echo "POSTGRES_PASSWORD=$DB_PW"
sed -i "s|^POSTGRES_PASSWORD=.*|POSTGRES_PASSWORD=$DB_PW|" .env

docker compose up -d postgres
docker network inspect sentriq_default \
  -f '{{ (index .IPAM.Config 0).Gateway }}'
Check — note the address, you need it next 
docker compose ps postgres
# sentriq-postgres-1  ...  Up (healthy)  5432/tcp
# gateway, typically 172.18.0.1
Why the password is set before the first start Postgres initialises its cluster with POSTGRES_PASSWORD on first boot only — later edits to .env do not change it. Generating it here and reusing the same value in step 07 keeps the database and DATABASE_URL in agreement without an ALTER USER afterwards.

07Write .env

Generate the two secrets, then fill in the file. Everything below is required unless marked optional.

openssl rand -hex 32   # APP_SECRET_KEY
openssl rand -hex 32   # EVIDENCE_ENCRYPTION_KEY
# the database password is the one step 06 generated and printed
nano /opt/sentriq/.env
APP_ENV=production
COOKIE_SECURE=1
ALLOWED_HOSTS=sentriq.example.com
PUBLIC_BASE_URL=https://sentriq.example.com

APP_SECRET_KEY=<openssl rand -hex 32>
EVIDENCE_ENCRYPTION_KEY=<openssl rand -hex 32>

POSTGRES_PASSWORD=<the password printed in step 06>
DATABASE_URL=postgresql://sentriq:<same password>@postgres:5432/sentriq

TRUSTED_PROXIES=<gateway from step 06>/32
WEB_CONCURRENCY=1
Two values you must not get wrong TRUSTED_PROXIES is the single address the proxy connects from — the gateway, with /32. A range like 172.16.0.0/12 lets any container claim any client IP, which defeats the rate limits and poisons the audit trail. ALLOWED_HOSTS is the domain only; adding localhost or an IP widens the Host allow-list for no benefit.
Keep a copy of EVIDENCE_ENCRYPTION_KEY It is not derivable. Lose it and every encrypted evidence file on the host is unrecoverable, including the ones inside your backups. Put it in your password manager or secrets store now, not later.

08Pin the database timezone

Sentriq stores timestamps as UTC in timestamp without time zone columns. That is correct only while the database session timezone is UTC — true on a default droplet, not guaranteed on a corporate cluster or a host with TZ set. Make it a guarantee with an override file, which also puts a ceiling on memory:

nano /opt/sentriq/docker-compose.override.yml
services:
  postgres:
    command: ["postgres", "-c", "timezone=UTC", "-c", "log_timezone=UTC"]
    mem_limit: 384m
  sentriq:
    mem_limit: 384m
  retention:
    mem_limit: 96m
Why an override file docker-compose.override.yml is merged automatically and stays untracked, so pulling a new release never conflicts with your host settings. Memory limits matter because without them the kernel OOM killer chooses which container dies — and it often chooses Postgres.

09Start the stack

cd /opt/sentriq
docker compose up -d
docker compose ps
Check — all three services up, the app healthy 
sentriq-postgres-1    Up (healthy)
sentriq-retention-1   Up
sentriq-sentriq-1     Up (healthy)   127.0.0.1:8080->8080/tcp

If a container is Restarting (1), the app is refusing to start and the reason is in the log — the config guards name the fix:

docker compose logs --tail=40 sentriq
If you changed the password after Postgres first started The cluster keeps the password it was initialised with. Either restore the value from step 06 in both places, or set it inside the database and recreate the app: 
docker compose exec -T postgres psql -U sentriq -d sentriq \
  -c "ALTER USER sentriq WITH PASSWORD '<the password in .env>';"
docker compose up -d --force-recreate sentriq retention

10Put nginx in front of it

Replace the ACME-only site with the real one. Note the listen 443 ssl http2 form — that is the syntax for nginx 1.24, which is what Ubuntu 24.04 ships. On nginx 1.25.1 or newer, use listen 443 ssl; plus http2 on; instead.

sudo tee /etc/nginx/sites-available/sentriq >/dev/null <<'EOF'
limit_req_zone $binary_remote_addr zone=sentriq_login:10m rate=10r/m;

upstream sentriq_app {
    server 127.0.0.1:8080;
    keepalive 16;
}

server {
    listen 80;
    listen [::]:80;
    server_name sentriq.example.com;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }
    location / {
        return 301 https://$host$request_uri;
    }
}

server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name sentriq.example.com;

    ssl_certificate     /etc/letsencrypt/live/sentriq.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/sentriq.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers off;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;

    client_max_body_size 25m;      # keep in step with MAX_REQUEST_BYTES
    client_body_timeout 60s;

    server_tokens off;
    proxy_hide_header Server;
    proxy_hide_header X-Powered-By;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "DENY" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    location = /login/ {
        limit_req zone=sentriq_login burst=10 nodelay;
        proxy_pass http://sentriq_app;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
    }

    location / {
        proxy_pass http://sentriq_app;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
    }
}
EOF

sudo nginx -t && sudo systemctl reload nginx
The one header people forget X-Forwarded-Proto https is what stops the app building http:// asset URLs on an https:// page. Omit it and the login page loads unstyled with the CSS and JS blocked as mixed content — which looks like a broken app, not a proxy bug.

11Create the first administrator

cd /opt/sentriq
docker compose exec -T sentriq python -m sentriq.manage create-admin admin_l3

It prompts twice and enforces complexity. Then sign in at https://sentriq.example.com/.

Exactly one administrator Create one. If you need a second, create it in Administration → Users and deactivate any setup account you are not using — is_admin accounts are the whole blast radius. Deactivation keeps attribution on old tickets; deletion is refused by design once an account has touched a ticket.

12Prove it works — eleven checks

Run these before you tell anyone the system is up. Each one fails loudly if the thing it tests is broken.

From the host

# 1. liveness, including backup freshness
curl -fsS http://127.0.0.1:8080/healthz
# {"status":"ok","database":"ok","backup":{"age_hours":0.0,"stale":false}}

# 2. the database is really on UTC
docker compose exec -T postgres psql -U sentriq -d sentriq -tAc "show timezone"
# UTC

# 3. migrations reached the head revision
docker compose exec -T postgres psql -U sentriq -d sentriq -tAc "select version_num from alembic_version"
# 0011_audit_append_only

# 4. the container is not running as root
docker compose exec -T sentriq id
# uid=100(app) gid=101(app)

# 5. through the proxy, with the certificate
curl -fsS https://sentriq.example.com/healthz

# 6. the app port is not published on the LAN interface
ss -tlnp | grep 8080
# 127.0.0.1:8080  (not 0.0.0.0)

From another machine

# 7. only 22/80/443 answer; 8080 and 5432 must not
for p in 22 80 443 8080 5432; do
  timeout 3 bash -c "</dev/tcp/sentriq.example.com/$p" 2>/dev/null \
    && echo "$p open" || echo "$p closed"
done

# 8. http redirects, https answers
curl -sI http://sentriq.example.com/ | head -3
# HTTP/1.1 301  Location: https://sentriq.example.com/

# 9. the certificate is trusted, not self-signed
curl -sS https://sentriq.example.com/ -o /dev/null -w '%{http_code}\n'
# 303 — no -k flag, so a bad certificate would have failed here

In the browser

  • No certificate warning. The padlock is real, not clicked through.
  • Sign in and load a page with the CSS intact. Unstyled means X-Forwarded-Proto is missing.
  • Create a ticket with a small attachment, download it again, and open the audit log. That exercises upload, hash check, download audit row and the timeline in one pass.

13Backups: schedule, verify, alert

The container snapshots the database on every start. That is not a backup schedule — a host that runs for a month would have one month-old dump. Add both cron jobs.

sudo -iu sentriq crontab -e
# daily snapshot, keep 30, no minimum interval
0 2 * * * cd /opt/sentriq && docker compose exec -T sentriq sh scripts/backup-postgres.sh /app/backups 30 0 >> /var/log/sentriq-backup.log 2>&1

# weekly restore drill: restores the newest dump into a throwaway database and compares row counts
30 3 * * 0 cd /opt/sentriq && docker compose exec -T sentriq sh scripts/verify-restore.sh /app/backups >> /var/log/sentriq-restore.log 2>&1

# every 30 min: shout if the newest snapshot is stale
*/30 * * * * curl -fsS http://127.0.0.1:8080/healthz | python3 -c 'import json,sys; sys.exit(1 if json.load(sys.stdin)["backup"]["stale"] else 0)' || logger -t sentriq "BACKUP STALE"
# keep the two logs from growing without limit
sudo tee /etc/logrotate.d/sentriq >/dev/null <<'EOF'
/var/log/sentriq-*.log {
    weekly
    rotate 8
    compress
    missingok
    notifempty
}
EOF
Check — run both jobs by hand once, now, not tomorrow 
cd /opt/sentriq
docker compose exec -T sentriq sh scripts/backup-postgres.sh /app/backups 30 0
docker compose exec -T sentriq sh scripts/verify-restore.sh /app/backups
docker compose exec -T sentriq python -m sentriq.manage backup-status
# newest snapshot, age in hours, stale: false
A degraded health check still returns 200 /healthz reports "stale": true after BACKUP_MAX_AGE_HOURS (36 by default) but keeps answering HTTP 200 — so the compose healthcheck keeps saying healthy. That is why the alert on backup.stale above is not optional. Point its non-zero exit at whatever already pages you.
Back up the secrets separately .env holds APP_SECRET_KEY, EVIDENCE_ENCRYPTION_KEY and the database password. Without the evidence key, an encrypted evidence file is unrecoverable even from a good dump. Store a copy outside this host — and do not leave .env.bak.* files in the checkout, where one git add -A publishes them.

14Retention and the audit export

The retention service archives and removes closed tickets older than RETENTION_DAYS (730 by default), in bounded batches, once at start and then every 24 hours. Nothing needs scheduling.

# dry run: shows what would be archived, writes and deletes nothing
docker compose exec -T sentriq python -m sentriq.manage retention

# pause or resume the job
docker compose stop retention
docker compose start retention

# hash-chained audit export, pushed somewhere this host cannot rewrite
docker compose exec -T sentriq python -m sentriq.manage audit-export --push --to-dir /app/backups/anchor
docker compose exec -T sentriq python -m sentriq.manage audit-verify /app/data/audit-exports/<file>
The append-only guard python -m sentriq.manage audit-guard reports whether the audit table is protected against UPDATE and DELETE by a trigger and by role privileges. Run it once after install; if it says the application role can still rewrite the trail, apply --app-role as the table owner.

15Updating, and rolling back

Pull a published image (preferred)

cd /opt/sentriq
sed -i 's|^# SENTRIQ_IMAGE=.*|SENTRIQ_IMAGE=registry.example.com/sentriq:1.4.4|' .env
docker compose pull
docker compose up -d --no-build
docker compose logs --tail=40 sentriq

Build on the host (when there is no registry yet)

cd /opt/sentriq
git fetch --tags && git checkout v1.4.4
docker compose build
docker compose up -d
docker compose logs --tail=40 sentriq
Rollback is not symmetric Migrations are forward-only. Going back to an older image after a migration ran needs the database restored to the matching snapshot — take one immediately before every upgrade (backup-postgres.sh) and keep it until the new version has been signed off. Rolling back the image alone will start, and then fail on a schema it does not know.

16Troubleshooting

SymptomCause and fix
Container Restarting (1)A config guard refused to start. docker compose logs sentriq names it: placeholder APP_SECRET_KEY, COOKIE_SECURE=0 in production, missing ALLOWED_HOSTS or TRUSTED_PROXIES, or several workers without REDIS_URL.
400 Bad RequestThe Host header is not in ALLOWED_HOSTS. Add the domain you are actually using, then docker compose up -d --force-recreate sentriq.
Login page unstyled, CSS/JS blockedX-Forwarded-Proto https is missing at the proxy, or TRUSTED_PROXIES does not include the gateway, so the app builds http:// asset URLs. Fix the header, recreate, hard-refresh.
502 Bad Gateway from nginxThe app is not healthy. docker compose ps, then docker compose logs sentriq. nginx is fine; the container is not.
PermissionError: /app/data/evidenceThe bind mounts are not writable by uid 100. sudo chown -R 100:101 data backups.
pg_dump ... Permission deniedSame ownership fix, on backups/.
Everyone is rate-limited at onceTRUSTED_PROXIES is wrong, so every request looks like it came from one address. Set it to the single gateway address and recreate.
Certificate renewal failsThe ACME location block is missing from the port-80 server, or /var/www/certbot is not readable by nginx. sudo certbot renew --dry-run proves it.
Timestamps look shiftedThe database session timezone is not UTC. Check show timezone; apply the override from step 08 and recreate Postgres.

17What "done" looks like

  • SSH is key-only; PermitRootLogin no and PasswordAuthentication no verified with sshd -T
  • ufw active with only 22/80/443; fail2ban running on sshd
  • Domain resolves, certificate is trusted in a browser with no warning, renewal timer scheduled
  • /healthz returns ok through nginx, and show timezone returns UTC
  • Ports 8080 and 5432 do not answer from outside the host
  • Exactly one active administrator; the setup password has been replaced
  • Daily backup cron installed, and a restore has been run by hand once
  • An alert fires when backup.stale becomes true
  • .env is mode 600, its two keys are stored off-host, and no .env.bak copies exist in the checkout
  • The running image is a tagged, scanned build — not a working-tree build of main
